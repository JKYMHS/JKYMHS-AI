## 1. 개요

### 1.1 서비스
TourAPI(한국관광공사) 관광지·축제 데이터로 국내 여행 코스(당일–3박 4일)를 짜 주는 데스크톱 웹 서비스입니다.

### 1.2 역할 분담 [확정]

**Spring이 후보를 고르고, AI가 그 후보로 코스를 엮습니다.**

| 단계 | 담당 | 내용 |
|---|---|---|
| 요청 접수, 횟수, 진행 상태, 결과 보관 | Spring | 202 응답 후 FE polling, 결과는 Redis에 24시간 |
| 후보 고르기 | Spring | 인기 순 200곳 → 회원 점수로 40곳 + 꼭 포함 장소 |
| **코스 구성** | **AI** | 후보 40곳으로 코스 3개를 짭니다. 장소 순서, 체류 시간, 추천 이유, 코스 제목과 요약 |
| 검증, 위반 시 재요청 | Spring | 규칙을 어기면 위반 목록을 붙여 AI에 1회 다시 요청 |
| 기본 추천 코스 | Spring | AI가 실패하거나 두 번 다 규칙을 어기면 가까운 순으로 만듦 |
| 시각, 이동 경로, 식사 칸 | Spring | 경로 서비스와 근처 음식점 서비스 |
| **장소 정보 보강** | **AI** | 설명문·태그·임베딩을 배치로 만들어 코스 구성에 씀 |

모델 학습이나 파인튜닝은 하지 않습니다.

### 1.3 목표

| 목표 | 기준 |
|---|---|
| 규칙을 지키는 코스 | Spring 검증을 첫 응답에서 통과하는 비율 90% 이상 (재요청 없이) |
| 빠른 응답 | 호출 1회 p95 10초 이내 (Spring 대기 한도 20초 안에서 재요청까지 가능하도록) |
| 서로 다른 3개 코스 | 3개 코스가 같은 장소로만 채워지지 않음 |
| 믿을 수 있는 추천 이유 | 입력에 없는 사실(가격, 할인, 영업시간 등)을 쓰지 않음 |
| 개인정보 최소화 | LLM에는 결제 계정으로만 보내고, 사용자 식별 정보는 보내지 않음 |

## 3. 코스 구성 (FUNC-003-02)

### 3.1 입력 (Spring이 보냄)

| 항목 | 내용 |
|---|---|
| 조건 | 기간, 첫날 시작 시각, 동행(혼자·연인·친구·아이·부모님), 아이 연령대(영유아·초등·청소년), 페이스(여유롭게·알차게), 실내 위주 여부, 둘째 날부터의 시작 시간대, 첫날 출발지 좌표 |
| 취향 | 행동 데이터로 계산한 상위 분류 최대 5개와 점수 |
| 후보 | 점수 높은 순 최대 40곳 + 꼭 포함 장소. 장소마다 이름, 좌표, 소분류 이름, 실내·실외, 영업 시작·종료·입장 마감, 쉬는 요일, 축제 기간, 꼭 포함 여부 |
| 규칙 | 코스 수(3), 하루 장소 수 범위, 점심·저녁 시간대, 아이 동반이면 20시 이후 금지 |
| 위반 목록 | 다시 요청할 때만. 직전 응답이 어긴 규칙 |

### 3.2 출력

| 항목 | 규칙 |
|---|---|
| 코스 | 정확히 3개 |
| 코스 제목·요약 | 코스마다 성격이 드러나게(예: "인기 명소 코스", "여유로운 동선 코스", "숨은 명소 코스") |
| 일차 | 1일차부터 마지막 날까지 하루씩 모두 |
| 장소 | 하루 장소 수 범위 안. 후보에 있는 장소만. 한 코스 안에서 중복 없음. 꼭 포함 장소는 모든 코스에 포함 |
| 체류 시간 | 분 단위. 비우면 Spring이 90분으로 채움 |
| 추천 이유 | 장소마다 40자 이내 [건의: 계약에 명시] |

### 3.3 코스를 짤 때 지킬 것

Spring 검증(`CourseValidator`)과 같은 규칙입니다. AI가 먼저 지켜야 재요청이 줄어듭니다.

| # | 규칙 |
|---|---|
| 1 | 코스 3개, 일차 1–N 하루씩 모두 |
| 2 | 하루 장소 수가 규칙의 범위 안 (여유롭게 2–3, 알차게 4–5, 아이 동반이면 하나씩 줄임) |
| 3 | 후보에 있는 장소만, 한 코스 안에서 중복 없음 |
| 4 | 꼭 포함 장소가 모든 코스에 있음 |
| 5 | 쉬는 요일에 넣지 않음, 축제는 축제 기간 안의 날에만 |
| 6 | 방문 시각이 영업시간 안 (꼭 포함 장소는 예외) |
| 7 | 아이 동반이면 20시 전에 끝남 |

**동선**: 같은 날 장소는 서로 가깝게 묶고, 첫날은 출발지에서 가까운 곳부터 시작합니다. 점심·저녁 시간대에 식사할 틈이 생기도록 체류 시간을 정합니다. 식사 칸은 Spring이 넣습니다.

**동행·스타일 반영**
- 아이 동반: 체험·실내 위주, 체류 시간 넉넉히
- 부모님: 걷는 거리가 짧은 동선
- 실내 위주: 실내 장소를 우선(실외를 빼지는 않음)
- 취향 상위 분류: 해당 분류의 장소를 우선

### 3.4 서로 다른 3개 코스

| 코스 | 성격 |
|---|---|
| 1 | 인기·대표 명소 위주 |
| 2 | 이동이 짧은 여유로운 동선 |
| 3 | 취향 분류와 덜 알려진 장소 위주 |

꼭 포함 장소를 뺀 나머지 장소가 세 코스에서 많이 겹치지 않게 합니다(목표: 코스 사이 겹침 50% 이하). [제안]

### 3.5 추천 이유

| 규칙 | 내용 |
|---|---|
| 근거 | 후보 정보와 보강한 장소 정보(분류, 태그, 설명문)에 있는 내용만 |
| 금지 | 가격, 할인, 영업시간, 주차, 예약 여부, 확인할 수 없는 수식어("최고의", "꼭 가야 할") |
| 길이 | 40자 이내 |
| 위반 시 | 그 장소의 이유만 기본 문장("{분류} · {동행}에게 추천")으로 바꿈. 코스는 그대로 |

### 3.6 다시 요청 (위반 목록이 있을 때)

Spring이 위반 목록을 붙여 다시 부르면, 직전 응답의 위반을 고친 코스를 돌려줍니다. 위반 목록은 한국어 문장입니다(예: "코스 2: 2일차 장소는 2~3곳이어야 합니다 (4곳)."). 다시 요청에도 위반이 남으면 Spring이 기본 추천 코스로 대신합니다.

## 4. 장소 정보 보강

Spring이 보내는 후보 정보는 이름, 분류, 시간뿐이라 코스의 성격을 정하거나 추천 이유를 쓰기에 부족합니다. AI가 배치로 장소마다 아래를 만들어 두고, 요청이 오면 후보 ID로 찾아 씁니다.

| 항목 | 내용 |
|---|---|
| 설명문 | 정해진 틀의 짧은 설명(분위기, 활동, 적합한 동행, 실내 여부, 소요 시간) |
| 태그 | 분위기, 활동, 동행 적합도, 접근성 |
| 권장 체류 시간 | 최소·보통 |
| 임베딩 | 설명문의 벡터. 개인화·후보 재정렬을 쓸 때만(6장) |

- 원문은 TourAPI 데이터(운영 DB의 장소·상세 정보)입니다. 원문에 근거가 없는 항목은 "정보 없음"으로 둡니다.
- 보강 정보가 없는 장소도 코스에 넣을 수 있습니다. 이름과 분류만으로 구성합니다.
- 운영 DB의 상세 정보(개요)는 장소의 약 20%만 채워져 있습니다. 수집 범위는 Spring 담당에게 확인 중입니다 [미결].

## 5. 실패와 대체

| 상황 | AI 서버 | Spring |
|---|---|---|
| LLM 시간 초과·오류 | 오류 응답(5xx)을 빨리 돌려줌 | 기본 추천 코스 |

**횟수**: 기본 추천 코스도 하루 횟수 10회에 포함됩니다. 실패(FAILED)만 빠집니다. Spring 구현을 따릅니다. [확정]

| 비용 | LLM 월 예산을 정하고 80%에 알림 [미결: 금액] |
| 데이터 출처 | TourAPI 이용 조건(출처 표시, 이미지 권리)을 지킴 |

## 8. Spring·FE에 건의할 것

### 8.1 계약 (`AiCourseRequest`)

| # | 건의 | 이유 |
|---|---|---|
| 1 | `conditions`에 `accessibleOnly` 추가 | 이동 편의 토글(유모차·휠체어·오래 걷기 어려움)이 지금 추천에 쓰이지 않음 |
| 2 | `reason` 40자 이내를 계약에 명시 | 응답 크기와 지연을 줄임 |
| 3 | 코스 1–3개 응답 허용 | 3개 중 1개만 실패해도 지금은 전체가 기본 코스로 바뀜 |
| 4 | (결정 3에 따라) `profile`에 최근 찜·저장 장소 ID | 임베딩 기반 개인화 |
| 5 | (나중에) 후보 재정렬 API | 인기 점수가 0인 동안의 후보 품질 |

### 8.2 Spring 운영

| # | 건의 | 이유 |
|---|---|---|
Spring 담당이 코드로 확인한 결과(2026-11-26)를 반영했습니다.

| # | 건의 | 이유 | 순서 |
|---|---|---|---|
| 1 | 스키마 관리를 `ddl-auto: update`에서 **Flyway**로. 현재 운영 스키마를 baseline으로 잡고, 다음 버전에서 고침 | 운영 CHECK 제약 32개 중 `LOCATION` 하나가 enum과 어긋남(위치 동의 저장 시 DB 오류). 열 이름을 바꾸면 옛 열이 조용히 남음 | 먼저 |
| 2 | 위치 동의(`LOCATION`) CHECK 제약 수정 | 1번의 첫 마이그레이션 | 1번 다음 |
| 3 | AI 배치가 읽을 view(`ai_content_source`) 제공 | 테이블 직접 권한은 AI 코드를 테이블 구조에 묶음. `ddl-auto`로는 view를 관리할 수 없어 1번이 필요 | 1번 다음 |
| 4 | **후보 풀의 동점 정렬 바꾸기** | 인기 점수가 모두 0이라 `ORDER BY popularity_score DESC, id`가 **지역마다 `contentid`가 작은 200곳만** 계속 고름. 같은 장소만 반복해서 추천됨 | 바로 |
| 5 | 늦게 시작한 요청은 바로 실패 처리하고, 정리 배치를 짧게 | 정리 배치가 매시 30분에 돌아 멈춘 요청이 10–70분 남음. 대기열 끝 요청은 시작까지 최대 3분 기다려, FE가 포기한 뒤에 AI를 부름 | 바로 |
| 6 | 취향 프로필의 **신뢰도 배수** | 새 행동이 없으면 감쇠가 저장값에 반영되지 않음. 다만 같은 배수가 모든 행에 곱해져 최댓값 정규화로 사라지므로, 감쇠 대신 가중치 자체를 줄여야 함 | 회원이 생기기 전 |
| 7 | Redis 영속 설정 확인 | 재시작 시 결과·진행 상태가 사라지는지 | 바로 |

**4번 제안**: 동점일 때 ① 정보가 충실한 장소(상세 개요·대표 이미지·영업시간이 있음)를 먼저, ② 그다음은 `id` 대신 날짜와 `id`의 해시 순으로 매일 바뀌게. 근본 해결은 회원이 없을 때의 초기 인기 점수나 AI 후보 재정렬(6장)입니다.

**5번 제안**: ① 작업을 시작할 때 요청 후 30초(FE 대기 시간)가 지났으면 AI를 부르지 않고 바로 FAILED. ② 정리 배치는 1분마다, 기준은 5분(서버 재시작 같은 사고 대비). ③ 대기열을 50에서 약 10으로 줄여, 30초 안에 시작할 수 없는 요청은 바로 503을 받게. 대기 시간 ≈ (앞에 있는 요청 수 ÷ 스레드 8) × 작업 시간(약 10초)이므로, 대기열 10이면 앞 요청이 다 차도 약 13초 안에 시작합니다. ①은 꼭 필요하고, ③은 실측 작업 시간으로 조정합니다.

**6번 제안**: 후보 점수의 프로필 가중치 0.4에 `신뢰도 = min(1, 행동 수 ÷ 10) × 0.5^(마지막 활동 후 일수 ÷ 30)`를 곱하고, 줄어든 만큼을 인기 가중치로 옮깁니다. 오래 쉰 회원이나 행동이 적은 회원은 취향보다 인기를 더 믿게 됩니다.
